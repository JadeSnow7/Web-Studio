## 1. 目标与交付日期

### 1.1 本次交付目标

在一套固定模板和固定初始数据上，演示并复验以下三类跨层修改：

1. 新增一个持久化字段。
2. 修改一个服务端权限规则。
3. 修复一个前后端字段不一致问题。

每个用例都要产生可查看的代码差异、真实运行结果和固定验收证据。单次成功演示只支持该次结果，不外推为通用开发成功率。

## 2. 仓库起点与技术范围

### 2.1 已核对的仓库起点

本计划以 2026-10-05 读取的远端基线 `f377db874f0ecba3390804146776b5e5786d2f86` 为起点，做了文档及 Agent 相关源码静态阅读，没有为本文重新运行原生构建或产品验收。

| 当前起点 | 对计划的影响 | 仓库依据 |
| --- | --- | --- |
| 主产品为 SwiftUI / AppKit / WebKit 的 macOS 工作空间 | 新增比赛代码采用 TypeScript；不把现有产品整体迁移语言列入排期 | [README](../../README.md)、[源码指南](../source-guide/README.md) |
| 网页资源使用 `WKWebView` | Chromium/CDP 路径需要独立建立和验证，不能把已有网页面板当作已具备 CDP 控制 | [README](../../README.md) |
| 现有 Codex CLI 问答路径显式只读、限制工具调用 | 比赛执行型 adapter 是新任务；不能直接把现有问答适配器记为已支持写代码和执行验收 | [AgentService.swift][baseline-agent]、[Agent 说明](../source-guide/05-agent.md) |
| 已有工作空间、终端、取消与进程管理相关实现 | 首日检查可以直接复用的部分；跨语言接入成本高时保留为参考，不为复用制造新框架 | [CodexProcessRunner.swift][baseline-runner]、[源码指南](../source-guide/README.md) |
| 仓库已有 Apache-2.0 许可证与第三方说明 | 沿用现有许可结构，补新依赖记录；不重新选择许可证 | [LICENSE](../../LICENSE)、[第三方说明](../../THIRD-PARTY-NOTICES.md) |

比赛执行入口独立呈现其工作目录、运行状态和取消行为。现有只读问答功能的限制不通过修改参数而被静默解除。具体实现路径在 T01、T02 中确认。

### 2.2 两层技术栈

| 层次 | 本轮默认方案 | 边界 |
| --- | --- | --- |
| 比赛工作台 UI | React + Vite；任务输入、预览入口、运行日志、证据列表 | 优先完成状态与结果；xterm.js 交互终端属于 P1 |
| 比赛工作台服务 | Node + Hono；WebSocket 推送有序运行事件 | 每个工作空间先只允许一个活动 run |
| 运行记录 | P0 使用 JSON / JSONL + 文件证据；SQLite 历史索引为 P1 | 数据库化查询不能阻塞真实闭环 |
| Agent | 一个现成 harness 的 headless 模式 + 薄 adapter | 不自研推理循环，不因 endpoint 兼容声明就判定工具兼容 |
| 协议 | Zod 定义任务、事件、验收结果的最小 schema | 仅保留后续替换 Rein 所需边界，不提前做通用运行时 |
| 浏览器 | Playwright 启动 Chromium；CDP 用于所需的观测与控制 | 开发预览与 Agent 操作绑定同一实际页面；E2E 可直接使用 Playwright |
| 唯一生成 App | React + Vite + Hono + Drizzle + Zod + Tailwind / shadcn | 不增加第二套模板 |
| App 数据库 | PGlite，由 App API 进程持有，使用持久化目录 | 不把浏览器内存数据库当作本轮后端持久化方案 |
| App 验证 | Vitest + Playwright；固定命令入口 | 有固定独立验收，也允许 Agent 补充应用自身测试 |

拟将比赛包放在 `competition/` 下，内部再组织 `apps/`、`packages/protocol/`、`templates/`、`fixtures/`、`acceptance/`。这些是待实现的目录约定，不表示当前仓库已存在。生成工作空间仅包含允许修改的 App 副本；固定验收与原始 fixture 留在生成工作空间之外。

### 2.3 本轮排除项

Rust 核心、自研 Rein 运行时、第二套模板、Expo / 原生移动端、生成 App 的上传功能、后台任务、实时协作、生成 App 的云部署、通用 WASM / Docker 沙箱平台、WebContainers、多 Agent 编排、复杂回放播放器。

本轮运行边界是本地固定模板与明确的工作目录。PGlite 是数据库；它不承担任意代码执行沙箱的职责。当前计划不承诺公共多租户或任意不可信仓库的安全运行能力。

## 6. 三个固定用例的验收约定

以下业务内容为建议值，可在首日修改；正式运行前冻结输入与验收版本。

| 用例 | 固定用户意图与初始条件 | 必须通过的验收 | 不能作为通过依据 |
| --- | --- | --- | --- |
| **C1 持久化字段** | 给任务增加 `priority`：low / medium / high，默认 medium；旧数据无此字段 | 新字段可编辑并保存；API 返回一致；旧记录迁移后仍可读；停止 API 并以同一数据目录冷启动后值保留 | 仅 UI 多一个输入框；仅刷新网页；重启前重新 seed 掩盖丢数据 |
| **C2 权限规则** | 将任务修改权限收紧为只有 owner 可修改；预置 A 的任务和 B 身份 | A 请求成功；B 直接 API 请求返回约定拒绝状态且数据不变；UI 错误与可用操作正确 | 只隐藏按钮；客户端自报 owner 即授予权限 |
| **C3 字段契约** | 固定契约使用 `dueDate`；初始前端错误使用 `deadline`，导致保存 / 展示失配 | schema / 类型检查通过；实际提交与 API 响应字段正确；保存后 UI 展示正确；关键原流程通过 | 放宽为任意字段；忽略失败响应；修改固定验收使其迁就错误输出 |

A/B 身份来自受控测试会话或现有认证路径，服务端按可信会话判断当前用户；不要把客户端请求中的用户 ID 当作权限证明。各用例单独恢复代码与数据库，不依赖前一用例的残留状态。

每个用例的目标验收应在初始状态检出问题，在正确修复后通过。C3 等故意带错的 fixture 只在专用生成副本中展开，不加入工作台或正常母模板的默认类型检查 / 绿色 CI；专门的验收应正确区分“预期初始失败”与“修复后仍失败”。

## 7. 最小运行与证据约定

### 7.1 标识和记录

| 字段 | 用途 |
| --- | --- |
| `workspaceId` | 定位生成 App 的工作目录与数据 |
| `runId` | 标识一次完整用户任务或一次独立复验 |
| `attemptId` | 标识该 run 内的一次修改与验收尝试 |
| `requestId` | 关联单个 HTTP 请求的前后端日志；按需记录 |
| `seq`、`timestamp`、`type` | 事件排序、时间与种类 |
| `mode` | `online` / `revalidate` / `replay` |
| `sourceState` | 基线 commit + diff / 内容哈希；不能只记录脏工作区的 HEAD |
| `fixtureVersion`、`acceptanceHash` | 明确初始数据和固定验收版本 |
| 结果与 artifact 引用 | 命令、退出码、错误、日志、截图 / trace、验收结果路径 |

最小事件包括：开始、attempt 开始、文件变更摘要、命令开始 / 结束、服务 ready、验收结果、证据新增、run 终态。由工作台归一化现成 harness 事件，未知事件可保留原文，不把解析缺失伪装成成功。

输出建议为一个 manifest、一份有序 JSONL 事件流，以及按需产生的日志、截图、Playwright trace。先覆盖三个用例，不制作通用追踪平台。

交付时把各用例最终源码快照和必要证据导出为仓库内样例或版本绑定的发布资产；源码必须包含新增文件、迁移与锁文件，不能只有未提交 diff。manifest 使用包内相对路径，记录快照哈希与原始基线。临时目录中的源代码和文件不可视为已经交付；必须在干净检出 / 下载后按同一入口完成复验。

### 7.2 数据与浏览器生命周期

- PGlite 在 API 进程中持有，每个工作空间使用独立持久化目录；验收数据与演示数据分开。
- API 活跃时，不让另一个验证进程直接打开同一数据库目录。优先通过 API 核对；确需独立 SQL 检查时，先完成关闭与所有权交接。
- 验收“持久化”必须包含进程停止和重启，且重启验证前不能重新写入预期数据。
- 记录预览对应的页面、URL、浏览器 context 和 App 实例；iframe 与另一个 Chromium 页面访问相同 URL，不足以证明共享同一登录和存储状态。
- 最终 E2E 可以创建全新 browser context，但须显式准备身份与初始数据。新 context 的结果与开发预览记录分别标识。
- 运行超时或取消时等待所属进程退出；终端界面停止输出不能代替进程清理完成。

### 7.3 三种模式及统计口径

| 模式 | 实际执行 | 是否调用模型 | 可证明的内容 |
| --- | --- | --- | --- |
| 在线运行 | 从固定初始状态请求 AI 修改，再运行验收 | 是 | 本次模型与配置完成任务的结果 |
| 无模型复验 | 启动指定最终代码，重新执行固定验收 | 否 | 当前环境下该代码仍满足指定验收 |
| 历史查看 | 读取旧事件与证据 | 否 | 过去记录了哪些结果 |

“无模型复验”不等于无网络安装：首次安装仍可能需要依赖与浏览器下载，README 应明确这一点。若评审环境要求全离线，另行核对依赖打包要求与成本。

指标至少记录用例、模型 / harness 版本、初始状态、预算、实际 attempt 数、通过与否、耗时、人工介入次数和失败原因。人工改代码、补关键提示、修改配置或手动恢复数据都应记入介入。在线运行、复验和历史查看分开统计；三个用例各跑一次就如实写“3 个样例、各 1 次”。

## 8. 拟固定的命令入口

以下是待实现的脚本契约，**不是当前仓库已有命令的说明**。统一从 `competition/` 目录执行，实际参数在 T03 / T09 落实到 README。

| 命令 / pnpm script | 约定 |
| --- | --- |
| `pnpm install --frozen-lockfile` | 使用锁文件安装；文档列明 Node、pnpm 和浏览器准备步骤 |
| `pnpm dev` | 启动比赛工作台 |
| `pnpm app:dev` | 启动指定生成工作空间的 API 与前端 |
| `pnpm db:migrate` / `pnpm db:seed` | 针对指定工作空间执行迁移与初始化；不隐式覆盖其他数据 |
| `pnpm check` / `pnpm build` | 固定类型、单元检查和构建入口 |
| `pnpm demo:reset` | 在专用演示目录恢复指定用例初始代码与数据 |
| `pnpm demo:run` | 指定用例和预算，启动真实在线 run |
| `pnpm verify` | 工作台控制的固定验收，失败时返回非零退出码 |
| `pnpm revalidate` | 指定最终代码与用例，无模型重新运行验收 |
| `pnpm replay` | 打开已有 run 证据，明确为历史查看 |

这些入口应显式接受工作空间 / 用例 / run 标识，记录实际命令与退出码。重置只能作用于已登记的演示副本，不能重置用户正在编辑的源仓库。

## 9. 风险与裁剪检查点

| 触发条件 | 处理 |
| --- | --- |
| 10/6 harness + 模型超过 2h 仍不能真实编辑和执行 | 使用已支持组合；压缩 provider 适配范围；不追加自研运行时 |
| 10/6 母模板不能稳定启动 | 先保留一个任务列表页面和最少 API，移除不影响三个用例的组件 |
| 10/7 结束仍无 C1 完整闭环 | 停止 UI 美化、原生壳整合、SQLite 索引、第二模型与交互终端 |
| 10/8 某个用例超时 | 缩小该用例业务范围，保持其跨层验收目标；停止新增通用权限 / 表单框架 |
| 10/9 复验仍依赖模型或人工补状态 | 优先修复准备数据、启动、验收和退出码；历史查看退回静态文件链接 |
| 10/10 冻结后发现问题 | 只修阻塞启动、验收真实性或提交的缺陷；变更代码后更新受影响结果与视频 / 版本引用 |
| 最终只有部分用例可复现 | 如实提交已完成用例与缺口；不把录制成功或回放包装成全部实时通过 |

三个用例、固定验收、真实证据和可运行说明是核心目标。若需要降低目标，由负责人修改本文并记录原因；不要静默放宽验收。
