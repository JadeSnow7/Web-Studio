# Web Studio 交互调研与候选方案

调研日期：2026-09-17。状态更新：用户已选择 B 路线，B1 核心已实现，完整验收未完成。本文为原调研时点的比较与建议，现状以 [当前状态](../../STATUS.md) 为准。

**建议把“可恢复的项目工作空间”作为中期方向，先完成现有工作台的交互收敛。** Web、终端与 Agent 已有共享资源基础，最值得解决的是“我在哪里、操作谁、哪些内容会发送、关闭后还剩什么”。进一步增加面板和入口，会放大这些问题。

本报告提供三套不同的产品组织方式，以及可以独立选择的交互细节。比较是基于当前代码、有限原生界面走查和官方产品资料的设计判断；没有用户访谈、使用频率数据或方案实验，不能据此宣称某方案已被验证更高效。

## 阅读与选择

| 候选路线 | 用户主要在做什么 | 核心改变 | 成本与边界 | 选择条件 |
| --- | --- | --- | --- | --- |
| **A：轻量资源工作台** | 打开页面、终端，随时问 AI | 保留当前布局，统一概念、目标和反馈 | 较低；不新增任务执行系统 | 希望尽快变好用，浏览与临时操作为主 |
| **B：项目工作空间（推荐）** | 长期维护多个项目，反复回来继续 | 工作空间记住资源配置、布局、入口和问题记录 | 中等到较高；需要持久化与恢复契约 | 跨项目切换、网页与终端协同是主要价值 |
| **C：任务驱动工作台** | 围绕一个目标组织上下文、进度和结果 | 任务成为导航主对象，资源成为任务材料 | 高；真正的执行型 Agent 另需权限、运行与产物系统 | 明确要把产品重心转向任务交付 |

以上成本是相对结构影响，尚无排期估算。A 可以成为 B 的第一阶段；C 应作为单独产品路线评估，避免同时维持三个同等级主导航。

## 方案 A：轻量资源工作台

**一句话：打开需要的网页和终端，明确地在它们之间切换、并排查看、提问。**

```text
┌ 导航按钮 ── [当前地址 / 目标类型] ── [当前资源 ▾] ─ 布局 ─ AI ┐
│ 分组 / 资源       │                                    │ AI │
│ 项目 A   网页 终端 │     网页，或终端，或左右并排         │问答│
│   文档      [左]  │                                    │    │
│   本地服务  [右]  │                                    │来源│
│ 项目 B            │                                    │问题│
└─────────────────┴────────────────────────────────────┴────┘
```

图中的左右标记放在导航行；内容区继续无固定标题栏。所有示例名称为方案示意。

用户从空白页打开资料，再新建本地终端；选择“与另一资源并排”，选中资料页。点击侧栏已有可见资源时只移动焦点；点击未显示资源替换当前焦点视图。加入 AI 后在输入框上方看到所选来源，读取并检查后发送。

主要变化：

- 将 Tasks / Workspace 收敛为“分组”；界面优先使用“网页”“终端”“SSH”，仅在通用管理处使用“资源”。
- 分组标题可折叠；折叠不切换内容。点击组名回到本组最后使用的资源；空组显示空状态，不因浏览分组而静默制造新资源。
- 保留每组的新网页、新终端按钮及现有快捷键；通过组菜单补充 SSH、指定目录终端。
- 默认 Split 改为选择器：“已有资源 / 新网页 / 新终端”，明确另一半将显示什么。
- AI 仍是单次问答工具；输入框常显“本次问题 + N 个快照”，保留精确预览。
- 普通网页关闭可提供“重新打开地址”；不得声称恢复未提交表单或完整页面状态。

**优点：** 与当前资源结构最接近；学习成本低；不会强迫轻量浏览进入项目管理。**代价：** 多项目的布局、对话和入口仍需用户管理；只改文案无法满足长期恢复。

第一阶段可以不引入持久化，但必须标注会话范围。“固定入口”长期保存可作为独立增量。已有不新增水平标签、不增加内容标题栏的视觉约束仍保留。

## 方案 B：项目工作空间

**一句话：为一件长期工作保存一套可重新进入的环境。**

```text
┌ [工作空间：Web Studio ▾] ── [当前地址] ── [布局 ▾] ── AI ┐
│ 当前空间          │                                    │问答│
│ 常用入口          │    文档网页       │   本地终端       │记录│
│   项目文档        │                   │                  │    │
│ 打开的资源        │                   │                  │来源│
│   文档       [左] │                   │                  │预览│
│   服务       [右] │                   │                  │    │
│ + 网页  + 终端    │                   │                  │问题│
└─────────────────┴───────────────────┴──────────────────┴────┘
```

工作空间不是新增一层嵌套目录。**直接把现在的分组升级为工作空间**：拥有名称、可选目录、资源描述、常用入口、布局、最后焦点和问答记录。窗口负责展示一个工作空间；跨空间的任务可以通过其他窗口进行。第一版不支持同一空间在多个窗口同时编辑，选择已打开空间时定位到其现有窗口，避免状态互相覆盖。

典型流程：

1. 创建“网站调试”工作空间，可选关联本地目录；添加文档地址、预览地址和终端目录。
2. 将预览与终端并排，布局与焦点自动记住。
3. 切去另一工作空间时保留原资源的会话内状态；不结束原终端，不把原资源自动加入新空间的 AI 请求。
4. 返回时恢复该空间的布局、焦点和草稿。
5. 应用重启后恢复资源列表与布局。网页按需重新加载；终端显示“待启动：目录 …”，SSH 显示“待连接：主机 …”。用户明确启动后创建新进程。

需要明确的保存边界：

| 内容 | 建议策略 | 用户可见说明 |
| --- | --- | --- |
| 空间名、入口、资源地址、目录、布局 | 本地持久化；支持删除配置 | “已保存工作空间” |
| 网页 Cookie / 登录 | 延续现有共享 WebKit 存储，暂不分空间隔离 | 设置中说明“工作空间共享网站登录状态” |
| 网页正在运行的 JS、表单、内存历史 | 不承诺跨退出恢复 | “重新打开网页” |
| Shell / SSH 进程与认证 | 不承诺恢复；显示待启动或待连接 | “上次会话已结束” |
| 问题草稿与问答记录 | 可选本地保存，设计清除与保留规则后启用 | “仅保存在此设备”需有真实实现 |
| 终端正文与发送快照 | 第一版默认不额外持久化；若需审计或恢复单独选择 | 明确保存内容与用途 |

历史回答若持久化而原始快照未保存，应标注“原始上下文未保留，无法原样重试”，重新读取后是新请求。不能用当前页面伪装原请求证据。

**优点：** 直接解决反复搭环境、切换项目、回来继续的问题；与资源/视图分离的架构相容。**代价：** 数据迁移、恢复失败、路径变化、跨窗口所有权和存储范围需要先定义；首次启动不能只增加一个“项目名称”表单。

与现有契约的差异是持久化、空间级布局与问答归属。选择本方案后才更新 DESIGN/UX 契约。本次不把这些建议写成已生效规则。

## 方案 C：任务驱动工作台

**一句话：先确定要完成的事情，再组织资源、过程与结果。**

```text
┌ 工作空间 ▾ ── 当前任务：排查登录异常 ── [问答 / 执行能力说明] ┐
│ 任务列表         │      当前资料 / 终端 / 结果              │
│ 排查登录异常     │                                         │
│   已选材料  2    │                                         │
│ 对比接口方案     ├─────────────────────────────────────────┤
│ 已归档           │ 任务问题、上下文、过程记录、完成依据       │
└────────────────┴─────────────────────────────────────────┘
```

在本方案中，任务有目标、材料、讨论与结果。网页和终端仍能手动打开，但导航优先回答“正在做哪件事”。选择任务恢复它引用的资源和会话，而非让每个任务复制一份所有终端。

应分为两个有明确边界的阶段：

- **C1：问题与资料组织。** 可以用现有只读问答能力验证；状态采用“草稿、提问中、已回答、已归档”。“已回答”只说明得到回答，任务完成由用户决定。
- **C2：可执行任务。** 另需真实工具、权限、取消和恢复语义、运行记录、产物与验证结果。届时才引入“执行中、等待批准、待验收”等状态。

用户可以选择一个目标，添加资料与终端快照，连续讨论，再把结论存入任务。未来执行型 Agent 修改了内容后，应展示实际变更、验证及剩余问题；不可用“正在思考”的动画代替这些状态。

**优点：** 对复杂目标和多轮工作最自然，后续可承载 Agent 工作流。**代价：** 轻量浏览多一个任务管理层；任务、对话、运行容易再度混淆。当前 `AgentRun` 只表示一次问答请求，不能直接重命名后充当完整任务。

适合在用户使用记录表明“多数时间围绕一个目标、多次提问并回顾结果”后重点推进。当前缺少这项证据，因此不推荐直接作为默认主界面。

## 可独立选择的交互细节

这些选择比颜色、磨砂强度、动画速度更影响使用逻辑。推荐组合为 **B + D1a / D2a / D3a / D4a / D5a / D6a**，其中涉及新数据或请求语义的部分仍为 proposed。

| 决策 | 选项 a | 选项 b | 建议与原因 |
| --- | --- | --- | --- |
| D1 地址入口 | 保留 ⌘L 地址、⌘K 命令；地址显示类型与即将执行的动作 | 一个万能框，混合地址、搜索、命令、AI | **a**：延续已学会的键位，降低误执行；自然语言不静默转 Shell |
| D2 上下文准备 | 在输入框旁用一个面板完成选择、读取、检查；显式发送 | 首次授权后，每次发送自动抓取已选资源 | **a**：保持现有可审阅快照；b 会改变发送前可见内容与权限预期 |
| D3 AI 语义 | 近期清楚呈现单次问答，另加显式“引用上一问答” | 实现真正连续对话，默认携带历史 | **a 先行**；b 需上下文预算、历史范围、模型切换与隐私规则 |
| D4 分屏建立 | 选择“与…并排”，可搜索同空间资源 | 自动猜测另一资源或自动恢复上次组合 | **a**：默认可预测；B 的已保存布局可以单独恢复 |
| D5 收起与结束 | 保持 ⌘W 资源关闭；收起分屏用独立动作与键位 | ⌘W 改为仅隐藏视图，后台继续运行 | **a**：减少习惯迁移；b 需建立后台运行列表和退出政策 |
| D6 窄窗口 | 内容优先，侧面板按需打开，可切 AI 专注视图 | 三栏永久存在并持续压缩 | **a**：避免同类资源只剩图标；切换模式保留草稿、焦点和布局 |

地址栏建议示例：“打开网页 · 当前视图”“新建 SSH · 工作空间 A”“在 /项目目录 新建终端”。`user@host` 可以识别为 SSH，但按 Return 前先让用户看见识别结果。输入普通词时提供明确的“搜索网页”候选；搜索服务与默认行为需另定，不能把内部主机名静默发送给搜索引擎。

保留一条快捷路径和一条可见路径：鼠标用户无需记快捷键；键盘用户无需每次打开嵌套菜单。命令结果分为“资源”“操作”，同名资源同时显示工作空间与类型。搜索别名覆盖中英文术语；结果目标在面板打开后保持稳定。

### 将“选择资源—预览—发送”做成完整的一段操作

```text
输入问题
  → 添加来源（默认先显示当前空间；跨空间需显式选择）
  → 读取所选内容
  → 查看摘要：2 个来源 / 采集时间 / 截断或失败提示
  → 可展开精确文本
  → 发送这份快照
```

输入框上方常显来源标签；“加入 AI”后立即看到新增来源和“待读取”，不自动发送。首次配置通过明确的“配置 AI”按钮进入；不能仅把下一步写成不可点击的小字。

部分读取失败时，列出失败来源并提供“重读失败项”与“移除失败项”；继续发送前需要形成一份新的完整快照集合。旧版本始终与历史问题绑定。资源导航后可提示重新读取；没有可靠变化事件的终端只显示采集时间，不能假装精确判断内容是否过期。

重试按钮分清“用原快照重试”和“更新资料后重新提问”。后一项创建新请求。对话滚动在用户阅读旧消息时不强制跳到底部，改为“有新回答”入口。回答能复制，失败信息靠近失败的问题，而非仅显示在整个列表底部。

### 关闭、恢复与错误反馈

| 用户操作 | 推荐语义 | 必须可见的后果 / 恢复 |
| --- | --- | --- |
| 收起分屏 | 移除当前视图引用 | “终端继续在当前应用会话运行”；侧栏仍可打开 |
| 关闭网页 | 释放该网页运行时 | 可重新打开地址；不承诺表单或 JS 状态恢复 |
| 结束终端 | 终止当前 Shell 和所属子进程 | 确认显示资源名、目录或主机；默认可取消 |
| 隐藏 AI 面板 | 隐藏界面 | 请求继续与否需固定规则；建议继续，并在按钮显示真实运行状态 |
| 新建问答 | 创建新条目或清空现有条目，两者明确区分 | 有草稿时保留或提示；不能用“新增”掩盖覆盖 |
| 重启终端 / 重连 SSH | 新建会话 | 保留旧退出信息；新会话独立身份，避免把旧快照附错 |
| 退出应用 | 结束应用拥有的运行会话 | B 保存配置；重启后明确哪些需重新启动 |

资源状态放在侧栏与详情，正常终端保持无标题栏。后台失败可给持久但低干扰的标记；前台操作失败就在目标附近说明下一步。网页加载、SSH 进程运行、已认证连接、AI 已配置与实际响应是不同状态；没有观测能力时使用“状态未知”，不制造绿色成功标记。

### 空间分配与原生交互

保留 SF 系统字体、语义颜色、现有磨砂层与减少动态效果。单视图继续内容优先；分屏用现有边缘焦点配合侧栏“左 / 右”标记，地址栏也能说明所控制的一侧。第一次分屏可短暂提示，之后不持续遮挡内容。

900×560 下不把“每个视图有 180pt”当成可用标准。原型应比较：隐藏导航、临时打开 AI、AI 专注视图三种组合。具体切换宽度由长标题、中文输入、终端列数和真实网页验证后校准；不要先写死一个审美断点。

所有拖放功能都有菜单替代。Escape 只退出最上层临时操作；地址编辑、中文输入法组合、终端 Ctrl-C、应用快捷键分别测试。不能为了统一快捷键而吞掉终端和网页的正常输入。

## 对三套方案使用同一组场景比较

| 真实任务 | A | B | C |
| --- | --- | --- | --- |
| 临时打开文档，开终端执行检查 | 最直接 | 保留“临时空间”可避免建项目负担 | 若要求先建任务会拖慢操作 |
| 两个项目各有页面与终端，来回切换 | 需补记忆，布局仍偏窗口级 | 最符合空间恢复模型 | 适合按目标切换；项目与任务关系更复杂 |
| 对比网页与终端输出，提交 AI 分析 | 一个明确的快照流程即可 | 来源有空间归属，更容易回溯 | 材料与结果绑定任务，长期回顾更好 |
| 次日继续工作 | 依赖少量恢复功能 | 主要价值场景 | 需要同时恢复任务、对话与资源引用 |
| 多 Agent 执行并审查结果 | 不作为核心能力 | 可新增运行列表，但仍需后端 | 最适合承载，但当前依赖缺口最大 |

不做加权总分：没有真实任务频率，数字会掩盖产品定位选择。若日常主要是临时浏览和终端，选 A；若主要是持续项目工作，选 B；若准备把资源管理服务于 Agent 任务交付，选 C。

## 建议推进次序

| 阶段 | 交付内容 | 验收重点 | 前置决定 |
| --- | --- | --- | --- |
| 第一阶段：减少误解 | 统一术语；关闭与收起文案；AI 单次问答说明；新建行为；地址动作提示；明确分屏对象 | 用户能预测目标、后果与发送内容 | A/B/C 都需要；先确定界面语言 |
| 第二阶段：完成高频流程 | 上下文准备合并；命令目录；分组最后焦点；同名资源查找；窄窗模式 | 不丢草稿、不串目标，键盘和鼠标可完成同一任务 | D1–D6 |
| 第三阶段：空间连续性 | B 的数据模型、保存、迁移、重新进入与失败恢复 | 重启后配置一致；没有伪装原进程恢复 | 是否选 B；保存内容与保留规则 |

## 如何验证选择，而非凭喜好重做

先用同样内容制作 A/B 的可点击原型；C 先测纸面流程，验证用户是否愿意以任务为入口。建议首轮邀请 5–8 位目标用户，覆盖网页为主、终端为主及两者混用；这是发现问题的研究规模假设，不是统计显著性保证。若只有产品拥有者可参与，仍可逐场景验证，但结论只适用于个人工作流。

| 场景 | 观察内容 | 首轮通过条件 |
| --- | --- | --- |
| 从空白页打开网页，再创建指定目录终端 | 是否找得到入口、是否理解新增还是替换 | 无指导完成；原资源保持 |
| 切换两个空间后返回 | 是否找回原资源、布局、草稿 | 不靠回忆重新搭环境；记录多余动作 |
| 同名网页分别位于两个空间 | 搜索结果能否区分 | 选择正确对象，打开面板后不串目标 |
| 分屏中点击另一资源、收起终端视图 | 是否准确预测替换哪侧、进程是否结束 | 能在操作前说出后果；误结束次数为 0 |
| 选择网页和终端给 AI；其中一个读取失败 | 用户知道缺什么、发什么、如何继续 | 不静默漏来源；可明确移除或重读 |
| 预览后网页变化，再发送或重试 | 是否理解快照时间与历史绑定 | 能说明使用旧快照还是新内容 |
| 中文输入时 Return / Escape，切换焦点 | 是否误提交、吞字、焦点丢失 | 无误提交；退出面板后焦点合理 |
| 在 900×560 中完成浏览、终端和提问 | 面板操作、长标题、按钮是否可达 | 核心操作无截断、遮挡与强制丢草稿 |
| 重启应用后继续（B） | 是否把恢复配置误当进程存活 | 终端与 SSH 明确待启动；失败可恢复 |

记录每个场景的完成结果、用时、错误目标次数、找不到入口的次数、求助次数和操作后解释。A/B 顺序交叉，同类材料难度相当；保留当前版本作为基线。零误结束/零错误发送是关键约束；时间改善目标在第一轮基线后制定，不预先宣称“效率提升 30%”。

后续实现验证分四层：模型路由与生命周期检查、原生真实交互、配置好的模型/SSH 链路、目标用户任务观察。它们各自出结果，不用某一层替代全部验收。
